## 二、下一轮第一件事

### 目标

精修时，**用户没提到的模型段不许被重写**。验收：`workflow` / `rbac` 在
「给某页加模拟数据」这类指令下指纹**未变**。

### 为什么不是 Merge Patch

已经试过，接不进去。`v5_capability_executor.py:492`：

```python
model = run_spec_first(goal, refine=_spec_refine, ...)["model"]
```

spec-first 天生「从 spec 树重新生成」，出口**永远是完整模型**。合并器看到六段
齐全就判「没按补丁交付」，原样放行。**补丁语义和这条链的架构不兼容**——这不是
接线问题，是方案选错了。

`services/merge_patch.py` 本身是对的（RFC 7386 逐行实现，12 条测试 + 2 个变异
全咬住），留着不删：将来若有真正按补丁产出的生成器，直接可用。

### 正确修法

**沿用同一个文件里已经存在的做法**。`v5_capability_executor.py:478-481`：

```python
if _reuse_style:     print("精修沿用上一版风格段")
if _reuse_language:  print("精修沿用上一版设计语言")
```

「精修沿用上一版」这个模式仓里已经有了，**只是只用在风格段上**。把它扩展到
模型段：精修时未被指令涉及的段**直接从基线复制，不进重新生成**。

思路同 Kubernetes server-side apply 的**字段归属**——谁拥有哪一段，重新生成就
不许覆盖不属于它的部分。是本仓已有的惯用法，不是新发明。

要动的地方：`run_spec_first` 的参数契约 + spec-first 内部的分支。**比之前任何
一次改动都深，别在上下文余量不足时动。**

难点：怎么判断「指令涉及哪几段」。可选方案（按稳妥度）：

1. 让精修的 SPEC 步顺带声明它需要改哪几段（多一个字段，不多一次调用）
2. 默认只允许改 `datamodel` / `page`，其余段一律沿用，用 env 开关控制
3. 关键词启发式（**不推荐**，本仓对未标定的启发式一贯保守）

## 五、2026-08-17：0/6 的成分（真机实测，推翻了第一节的判断）

### 先说结论

做完方案 1（逐段沿用）之后真机跑了两轮，**沿用一段都没成功**——四次尝试全被
引用完整性闸拒绝。追下去发现根因不在沿用本身，而在一件从没被验证过的事：

> **id 每一轮都重新铸造。** 于是「逐段指纹 0/6」根本证明不了内容被重写——
> 它跟「内容一字没动、只是 id 换了一批」是同一个读数。

把两者分开量（社区养老平台，两轮，`page` 都是 5 页）：

| 对象 | 个数 | id 保住 | 名字保住 | 判断 |
|---|---|---|---|---|
| `page.pages` | 5→5 | **5/5** | **5/5** | **完全稳定**，指纹变纯粹因为引用了被改名的权限 |
| `rbac.roles` | 3→3 | **0/3** | **3/3** | **纯 id 抖动**：同样三个角色，id 全换 |
| `workflow.nodes` | 4→3 | 0/4 | 3/4 | 主要是 id 抖动，另少一个节点 |
| `appbundle` | — | — | — | 整段都是引用，跟着上面一起变 |
| `rbac.permissions` | 14→11 | 4/14 | — | 混合：改名 + 增删 |
| `datamodel.entities` | 5→4 | 1/5 | 2/5 | **真的重写**：`mall_service` 整个消失，字段成套换掉 |
| `aigc.capabilities` | 1→1 | 0/1 | 0/1 | **真的重写**：能力完全不同 |

id 漂移长这样（同一个角色，两轮三套名字）：

```
station_manager  →  role_station_manager  →  manager_role      「社区养老站长」
elder:read       →  care_order:read       →  elder_archive:read
wo_created       →  wf_pending            →  node_pending      「待派单」
```

**不是随机重铸，是近义漂移**：id 由概念名派生，派生规则稳定但用词不稳定
（`elder` / `elderly` / `elder_archive` 是同一个东西）。所以它**极易锁定**——
把上一版 id 表喂进去要求沿用即可，不需要重映射机制。

### 根因在链路结构里，一条 grep 就能确认

```bash
grep -c refine services/model_assembly.py services/spec_semantics.py services/html_structure.py
# 三个都是 0
```

refine 上下文**只到达第 2 步（SPEC）**。而铸造实体/角色/权限/流程节点 id 的是
第 4/5/6 步——它们对「有上一版」这件事一无所知。于是：

```
第2步  收到 refine，保住了页面名、角色名（实测 5/5、3/3）   ← 所以结构保住了
第4/5/6步  不知道有上一版，id 全部现铸                      ← 所以指纹全变
```

这也解释了为什么四次修复只保住结构、保不住指纹：**四次都改在第 2 步或它上游。**

### 为什么逐段沿用现在是惰性的

闸守的是引用完整性，而混合两轮的模型必然违反它——两个方向都堵死：

```
沿用 rbac              → 新生成的 page.actionPermissions 指向新权限 id，旧 rbac 里没有
沿用 rbac + workflow   → 同上
只沿用 rbac            → 新生成的 workflow.assigneeRole 指向新角色 id，旧 rbac 里没有
```

调换丢弃顺序救不了——`rbac` 是被依赖最多的那个，而 `page` 永远重新生成。
**只要 id 每轮重铸，任何跨轮混合都过不了闸。**

### 下一件事：id 稳定化（比之前设想的三个方案都轻）

不是改架构，是**补一份 id 表进第 4/5/6 步的提示词**，要求既有概念沿用既有 id。

做完之后：
- `page` / `rbac.roles` / `workflow` / `appbundle` 四段的指纹直接拿回来
- 闸的封锁解开，**已经提交的逐段沿用会自动开始生效**（它现在惰性，但机制和
  失败路径都验证过了，别回滚）
- 剩下 `datamodel` / `aigc` 是真重写，要单独处理。⚠ 注意 `datamodel` 被**排除**
  在可沿用清单之外（它跟第 3 步的 HTML 绑定），所以它需要的是另一套办法，
  不是把它加进沿用清单

### 验收方法要跟着改

**别再单用 raw 逐段指纹当判据**——它把 id 抖动和内容重写混成一个读数，
四次修复的选型就是被它误导的。至少要三把尺子并排：

```
raw          原样 sha256
抹 id 后      id 换成被引对象的名字、列表按内容排序
名字 Jaccard  每段里人类可读名字的集合相似度
```

⚠ 写这把尺子时踩到两个坑，别重犯：
1. 两边各用自己的 id→name 表解引用，会让**同一份字节**被判成"变"
   （引用的对象在新一轮没了）。结果"抹 id 后"比 raw 还低，荒谬。
2. 权限是**裸字符串**（`elder:read`），没有 `name` 字段，永远进不了 id→name 表。
   只靠这把尺子会得出"id 不是主因"的错误结论——**我第一版就是这么错的**，
   是回头直接看 `rbac.roles` 的原始数据（3/3 名字相同、0/3 id 相同）才纠正过来。

**量不清楚的时候，直接把两版数据摊开看比造尺子快。**

### 台子本身多做的三件事

1. **每轮自证开关生效**。`SLIDERULE_REFINE_ID_FREEZE` 走 env 传子进程，传丢了
   不报错，只会让两臂**悄悄变成同一臂**——那会跑出「看起来 n=10 其实 10 个 ON」
   的假数据，比 n=1 更糟。正反两条都验：本臂特征行必须在、对臂特征行必须不在。
   实测 10/10 双向全对。
2. **fail-closed 的 LLM 预检**：缺 key 直接拒绝启动。烧 40 分钟拿一堆 fallback
   是这类实验最贵的失败。
3. **两臂交替跑**，不按臂分块——网关状态、限流都随时间漂，分块会把「时间」
   混进「处理」里。

### 结果（同模型 flash-lite、同话题、同指令，只差开关；每臂 n=5）

| 对象 | OFF 各轮 | ON 各轮 | 判读 |
|---|---|---|---|
| `workflow.nodes` | 0.00 0.25 0.00 0.00 0.33 | **1.00 ×5** | 零重叠，最干净 |
| `rbac.roles` | 0.00 0.00 0.00 **1.00** 0.00 | **1.00 ×5** | 有一轮 OFF 也满分 |
| `rbac.permissions` | 0.58 0.36 0.70 0.36 0.75 | 1.00 0.82 0.90 1.00 0.88 | 无重叠 |
| `datamodel.entities` | 0.50 0.50 0.67 0.33 0.67 | 1.00 0.67 1.00 1.00 1.00 | **在 0.67 处重叠** |
| `aigc.capabilities` | 0.00 ×5 | 1.00 1.00 0.00 0.00 0.00 | 见下，别记在冻结头上 |
| `page.pages` | 0.00 0.00 1.00 0.00 0.00 | 0.00 0.00 1.00 0.00 1.00 | **两臂都双峰 = 噪声** |

### 被推翻的三条

**① 第六节那个 `page.pages` 0/3 vs 3/3 是运气。** 多轮下来两臂都在 0.00 和 1.00
之间跳，OFF 臂也出现过 1.00。它**既不在 `model_id_lexicon` 里、也不在
`REFINE_REUSABLE_SEGMENTS` 里**，本来就该自由漂——第六节把它列进疗效表是错的。

**② `aigc` 的改善不能全算冻结的功劳。** 它不在词表里，但**在可沿用段里**，
沿用过闸就整段照搬。而且 on-2 实测**没发生沿用，aigc id 照样没变**（模型自己
给了同一个 id，名字倒改了）。所以它是「经沿用的间接效应 + 一部分模型自发稳定」，
要连 `run.log` 一起读才归得了因。

**③ 「冻结开着就不会退让」不成立。** ON 臂 5 轮里 3 轮退让到空。

### 沿用失败的成因：8/9 是同一条

| 成因 | 次数 |
|---|---|
| 新生成的 page 引用了**沿用的旧 rbac 里没有**的权限 | 8 |
| aigc 字段悬空（旧有形态） | 1 |

第一版假设写的是「第二轮新增实体 ⇒ 沿用失败」，被 on-3 当场证伪：实体 3→3
没新增，照样退让，缺的是**已有实体上的一个新动作**（`service_staff:export`）。
推广后 8/9 零例外：`health_monitor:read`、`elderly:create`、`elder:read`、
`elder:create`、`elderly_monitor:read`、`community_branch:read`、
`service_staff:export`、`elderly:delete`。

**这不是 id 漂移，冻结救不了。** 冻结保的是「已有 id 别改名」，管不了「多出来
一条」。沿用是整段照搬，整段照搬天然容纳不了增量。

**修法方向已经有据**：ON 臂 4/4 复核，这些缺的权限**全是合法的**——对应真实
实体（2 条来自本轮新增实体、2 条来自旧实体的新动作），而且新生成的 rbac 自己
也铸了它们，零例模型凭空编造。所以：

- ❌ **别锁 page 的权限词汇表**——会禁掉这 4 条里的每一条，全是真实需求
- ✅ **让沿用的 rbac 吃增量**（沿用旧的 + 并上本轮合法新增）

这跟第 6 步锁词汇表为何是对的也自洽：第 6 步**消费**已定词汇，生成 page 那步
**产生**新需求，性质不同，不能套同一个约束。

### 顺手改掉的：退让顺序（前缀 → 1-maximal）

原来 `candidates.pop()` 从尾巴丢，可达组合**只有前缀**：
`{rbac,workflow,aigc} → {rbac,workflow} → {rbac} → {}`。而卡住的**永远是 rbac**
（上面 8/9），它排在最前、最后才被丢——丢 aigc 丢 workflow 纯属白费，等轮到它时
其余早已赔光。

离线 replay（`replay_reuse_search.py`，闸是纯函数可精确复算）：

```
OFF 臂 5/5   全枚举也找不到能过闸的子集   → 前缀退让零损失
ON  臂 3/3   {workflow, aigc} 每次都存在   → 前缀链每次都够不到
```

⚠ **因果方向别搞反：是 id 冻结制造了「部分稳定」，才让前缀限制开始咬人。**
OFF 臂 5/5 证明冻结之前这个改动一分钱收益都没有。**先后顺序不能倒。**

改法照 **ddmax**（Kirschner/Gopinath/Zeller, ICSE 2020；debuggingbook 的 `dd`
算法 `'+'` 模式）——ddmin 找最小致败子集，ddmax 反过来找最大的能通过子集，
终止于 1-maximal。借的是**判据**，不是它的分块二分（那是 n 很大时省测试次数用的，
这里 n=3 线性试加才对）。代价不涨：先整体试一次（成功就 1 次过闸，跟原来一样快），
失败再逐个试加，上界仍是 n+1。

拿**上线的那个函数**（不是 replay 里的副本）跑真机数据复核：on-2/on-3/on-5
三轮全部拿回 `{workflow, aigc}`。ON 臂保住段的轮次会从 2/5 变成 5/5。

判据 3 条（1 鉴别 + 2 护栏）、变异 4 个全咬住。⚠ 鉴别判据必须让**罪魁排在最前**
——原有那条 `test_只丢过不了闸的那段_其余保住` 的罪魁是 aigc、排在最后，从尾巴丢
第一下就丢对，前缀退让照样绿，**咬不住退让顺序这件事本身**。

### 网关故障：给那条「没有任何地方统计」一个初值

10 轮真机日志里 `[llm-retry] 第 N/M 次失败` 共 **5 次**（off 臂 1、on 臂 4），
形态包括 `RemoteProtocolError: peer closed connection`、`Server disconnected`、
`HTTP 502: upstream 502: policy context unavailable`、`ConnectTimeout`。
**网关问候语 0 次**（那两次「你好！我是 OuYi」这轮没复现）。

⚠ **这是绝对次数，不是发生率**——分母（本批总 LLM 调用数）没有埋点，算不出来。
要真正的发生率得在 `call_llm_with_retry` 里加计数，那是这条 open item 的下一步。

### 顺手修掉的一个真 bug：超时日志差 120 倍

跑批时从日志里捞到一行自相矛盾的：

```
[llm-retry] 第 2/3 次失败（可重试，耗时 5.2s）：timeout after 600s
```

`_http_timeout` 把 connect 压到 5s、其余留 600s，而 `ConnectTimeout` 是
`TimeoutException` 的子类，被那个 except 一把捞走后消息里填的是**配置的整体
预算**。5.2 秒正好就是 connect 超时。

跟 `_describe_http_error`（2026-08-14）是同一个病，当时**只修了 HTTPError 分支**,
紧挨着的 TimeoutException 分支漏了——两个 except 挨着写，看代码时特别容易略过。
危害：连不上（查网关可达性）和生成太慢（查模型/预算）修法相反，日志把前者写成
了后者。收尾那 821 秒的黑洞至今没定论，靠的就是这类分不出成分的日志。

### 还发现一件事：并发把日志写坏了

on-4 的日志里出现：

```
…aigc field 'elder.health_[html_bindings] 页面 p3 重问第 1 次：…
                          ↑ 没有换行，两条日志撞在一起
```

第 3 步页面生成是并发的，多线程 `print` 到同一个 stdout 不是原子操作。后果是
**聚合器判 on-4「未发生沿用」，而落盘模型显示 rbac/workflow 段指纹逐字节相同
——它明明沿用了**。

判据因此从「读日志」改成「量落盘模型的段指纹」。这是纪律五的原话：判据要落在
真正的产物上。日志是尽力而为的叙述，模型是事实；并发一撕，叙述就不可信了。
⚠ 这条对**所有**依赖日志的判据都成立，不止这一个脚本。

### 下不了的结论

- **每臂 n=5 仍是小样本。** 方向一致、幅度大，但没做显著性检验。
- **`datamodel.entities` 两臂在 0.67 处重叠**，`rbac.roles` 有一轮 OFF 也拿到
  1.00。只有 `workflow.nodes` 是真正零重叠。
- **`page.pages` 不该算疗效**（两臂都双峰）。
- **`aigc` 的数字混着两个来源**（沿用的间接效应 + 模型自发稳定）。
- **网关故障只有绝对次数，没有发生率**（缺分母）。
- **「让 rbac 吃增量」只定了方向，没实现**——怎么并、并进来的权限要不要过闸、
  会不会把用户明确要删的权限又并回来，都没想清楚。别照着这一节直接开写。

## 八、2026-08-17 深夜（续）：rbac 吃增量做完了

第七节把这条列在「下不了的结论」里，写着「别照着这一节直接开写」。现在做完了，
下面是当时那三个没想清楚的点各自的答案——**都是量出来的，不是拍的**。

### ① 怎么并：三种候选，闸判不出优劣，按原则选

| 并法 | on-2 | on-3 | on-5 | 结论 |
|---|---|---|---|---|
| A 旧 ∪ 新全部 | 过 | 过 | 过 | 会并进页面没引用的权限，没依据、累积快 |
| B 只沿用 roles、权限用新的 | 过 | 过 | 过 | **淘汰**，见下 |
| C 旧 ∪ 页面真正引用的 | 过 | 过 | 过 | ← 选它 |

三种都能过闸，所以**不能靠闸选型**。定 C 的理由是修法要跟病灶一样大：
并进来的每一条都有页面在引用它。

淘汰 B 的是数据：真机 on-2 新生成的权限**丢了** `work_order:export` 和
`work_order:manage`，而用户那轮只说了「加点模拟数据」。B 会让这两条凭空消失
——正是最初被抱怨的形态。其余 4 轮新的是旧的超集，只看那 4 轮会误判 B 没问题。

还有个观察省了不少事：ON 臂里 r1/r2 的 **roles 完全相同**（id 冻结已经管住了），
所以「沿用 rbac」对角色几乎是空操作，**唯一卡住的就是 permissions 那个列表**，
而且增量是纯追加的。

### ② 并进来的权限要不要过闸：不需要特殊处理

合并结果跟其余段一起组成候选，**再整份过一遍同一个闸**。这里没有任何特权通道
——伪造绿灯是红线。判据 `test_合并结果照样过闸_没有免检通道` 钉的就是这条。

### ③ 会不会把用户明确要删的权限并回来：不会

`spec_first_pipeline.py` 那句 `seg not in named`——**用户点名 rbac 时，
rbac 根本不进沿用候选**，合并自然走不到。这跟现有的整段沿用是同一个兜底，
合并不会让风险变差。判据 `test_用户点名rbac时根本不合并`。

### 结果（ON 臂 5 轮，用最终实现复跑真机数据）

| | 保住了点东西 | 三段全保住 |
|---|---|---|
| 真机当时（前缀退让） | 2/5 | 1/5 |
| + 1-maximal 退让 | 5/5 | 1/5 |
| + 权限合并 | 5/5 | **4/5** |

**旧权限一条没丢**（5/5）。on-4 的 aigc 是真悬空（datamodel 字段变了），
沿用不了是合法拒绝，4/5 是这批数据的上限。

### 变异咬出来的两个判据弱点（值得单独记）

**弱点一：判据被回落路径白送绿灯。** `test_页面引用的新权限被并进来` 第一版只写
`"wo:export" in perms`。把合并整个删掉时，rbac 会**回落到新生成的那份**，
而新的那份本来就有 `wo:export`——判据照样绿。修法：先钉死「rbac 确实是沿用来的」
（角色指纹 == 上一版），再看权限。

**弱点二：夹具没还原病灶。** `test_旧权限一条都不许少` 第一版咬不动「权限用新的」
那种退化实现，因为夹具里新权限是旧的**超集**，根本丢不掉东西。而真机 on-2
恰恰是丢了两条。修法：夹具让新权限**故意丢掉一条旧的**。

两条都是「测试自己长得像在测，其实没测」，跟本仓纪律二、三是同一件事。

### 判据与验证

9 条新判据（含 4 条反向），变异 5 个全咬住：不合并 / C→A / C→B / 只认字符串
形态的权限 / 合并了但日志不说。全量 3890 passed。

⚠ **日志必须说出并了哪几条权限**。「沿用 rbac」读起来是整段照搬，而这里其实
动了它的 permissions——不说就是「东西看着是旧的、其实改过」，出问题时对不出账。

### 仍然下不了的结论

- **没跑新的真机 A/B。** 上面 4/5 是拿**已落盘的 10 轮数据**离线复跑最终实现
  得出的，不是重新跑了 10 轮。离线复跑用的是真闸和真数据，但**第二轮的页面
  是在旧行为下生成的**——新行为可能让模型看到不同的上下文，进而产出不同的页面。
  要真正确认，得开着新代码重跑一批。
- **权限仍然只增不减。** 沿用路径永远不会删旧权限。多轮精修下来权限会单调累积
  （上界是 实体数 × 动作数，不会发散，但会变脏）。想清理得靠用户点名改 rbac。
- **只处理了 permissions，没处理 roles。** 真机 ON 臂角色天然稳定所以没暴露，
  但如果哪天新 workflow 引用了旧 rbac 没有的角色，会走回退让。同样的并法能不能
  照搬到 roles 上，没量过，别想当然。

## 九、2026-08-17 深夜（续）：开着新代码重跑真机 A/B

第八节的 4/5 是**离线复跑**已落盘数据得出的，自己标了局限：那些第二轮页面是在
旧行为下生成的。这一节把新代码真跑了一批。

台子：`ab_multi_run.py --arms v1,v2`，数据在 `runs-v2/`。
⚠ 这批跟第七节**不是同一个维度**：那里变的是 id 冻结，这里冻结**固定开**，
变的是沿用策略。别把两批的数字放一起比。

  v2 = 1-maximal 退让 + rbac 吃增量（现在的默认）
  v1 = 按序从尾巴丢 + 不合并权限（2026-08-17 傍晚之前）

为此加了两个独立开关（`SLIDERULE_REFINE_REUSE_1MAXIMAL` /
`SLIDERULE_REFINE_RBAC_MERGE`），**线上回退杆和对照臂两用**。分开是因为
1-maximal 单独就是净收益，万一线上是合并出问题，得能只退合并。

### 结果一：不配对（两臂各自端到端跑，每臂 n=5）

| | 三段全保住 | 丢了 workflow+aigc | 丢旧权限 |
|---|---|---|---|
| v1（老） | 3/5 | **2/5** | **1 轮丢 3 条** |
| v2（新） | **4/5** | 1/5 | 0/5 |

v1-2 丢的三条是 `service_report:create`、`service_report:manage`、`staff:approve`
——退让到空后整份用新 rbac，旧权限就没了。这是「退让」这件事的**直接伤害**，
比丢 workflow 更难被发现。

v2-1 那轮丢 workflow+aigc 是**合法拒绝**（aigc 的 inputFields 指的 datamodel
字段真的变了），不是新行为的问题。

⚠ **一个量法上的坑，记下来免得下次又踩：** 「角色有没有保住」不能只看指纹相等。
  v1-2/v1-5 日志明明写着退让到空（什么都没沿用），而 r1/r2 的 roles 指纹**照样
  相同**——那是 id 冻结让模型重新生成时给出了同样的 id，不是沿用。
  指纹相等 ≠ 沿用发生。要判「沿用有没有发生」得看 workflow/aigc 或日志。

### 结果二：配对（同一份输入，新旧算法各跑一遍）

不配对的比法有个硬伤：两臂是**各自独立的两轮**，第一轮产物不同，
「这轮碰巧没触发病灶」和「算法更好」混在一起。所以再做一次配对的。

只用**老行为下生成的 10 组输入**（on-1~5、v1-1~5）：

```
新算法保住得更多  5 组
持平              5 组
更差              0 组
新算法丢旧权限     0 组
```

⚠ **v2 那 5 轮的输入不能进这个配对分析**：它们的第二轮产物本身就是新行为的
  输出，拿去复算等于自己验自己。第一版脚本把 20 组全放进去了，虽然结论没变
  （5 好 10 平 0 差），但那 5 组 v2 是循环论证，不该计入。

### 顺带发现：权限前缀可以不是真实体，没有任何地方管

v2-1 的**第一轮**（被沿用的那份）自己就不自洽：

```
实体   elderly, service_order, subsidy_claim, care_schedule
权限   elderly:read, elderly:write, order:read, order:write,
       claim:read, claim:write, schedule:read, schedule:write
                   ↑ 简称，跟实体 id 对不上
```

第二轮页面用的是正确全名，合并把全名版加了进来，于是同一份 rbac 里既有悬空的
`order:read` 也有正确的 `service_order:read`。

量过了：**11/12 轮权限前缀全部对得上，只有这 1 轮有（6/117，5%）**。所以是模型
输出的偶发波动，**不是合并造成的**——第一轮就已经这样，整段照搬同样会搬过来。
合并唯一让它变差的地方：不合并的话这轮会退让、rbac 被重新生成，垃圾顺带冲掉。

但它带出一个上游真问题：权限约定形状是 `<实体id>:动作`，而**没有任何地方强制
前缀必须是真实体 id**。第 6 步早就锁死词汇表（"一个都不许新造"），铸权限那步
没有同款约束。闸也不查这个方向（它只查「页面引的权限在不在 rbac 里」）。

**没在这轮改**：1/12 的样本不够，而且删权限比加权限危险得多。留给下一个人。

### 仍然下不了的结论

- **每臂 n=5，没做显著性检验。** 不配对那组 3/5 vs 4/5 差距很小，单看它说明不了
  什么；真正的证据是配对那组的 5 好 / 5 平 / 0 差。
- **病灶触发率本身在飘。** 上一批 5 轮触发 3 轮，这批 v1 5 轮触发 2 轮。
  「新代码好多少」取决于多久触发一次，而这个数不稳。
- **权限仍然只增不减**，且现在有了具体实例（v2-1 的悬空前缀会被一直带下去）。
- **只做了 permissions，没做 roles。** 这两批角色天然稳定所以没暴露。
