# 区块目录去重审查（2026-08-11，两刀）

用户在组件库那面墙上一眼看出来的：**「现在的组件有很多是糊弄出来的，是表格」**。

这份文档记的是：怎么量的、量出什么、砍了什么、以及为什么老的防线没拦住。

## 一、先排除了三种"看着像但不是"的解释

用户说的是"表格"，但按 AST 依赖图数，**407 个区块里只有 22 个渲染了 Table**。
所以第一反应"目录里全是表格"是不成立的，得往下找。

| 试过的口径 | 结果 | 结论 |
| --- | --- | --- |
| 渲染里含 `Table/ProTable` | 22 / 407 | 不是它 |
| 渲染=只有表格+卡壳 | 1 / 407 | 更不是 |
| `rendererKey` 重复（老防线的口径） | **0 组**，407 个键全唯一 | 老防线在这儿看不出任何问题 |
| 桌面组件签名重复 | 230 / 407 涉及 | 太宽——23 个图表都是 `Card,ECharts,Empty`，可漏斗图和雷达图确实不是一回事 |

## 二、真正的口径：看实现，不看标识

把每个渲染器的源码抠出来、抹掉所有字符串字面量之后做哈希，**12 组完全相同**。
再往上追一层，根子是这个形状：

```ts
const QueryModeTabsRenderer     = stableTabsRenderer("query-mode-tabs", "查询模式", "itemSelect");
const DatasetEditorTabsRenderer = stableTabsRenderer("dataset-editor-tabs", "数据集编辑", "itemSelect");
const DocumentHistoryTabsRenderer = stableTabsRenderer("document-history-tabs", "文档历史", "itemSelect");
// … 一共 17 个，第三个参数**全是同一个值**

const WorkItemContextSummaryRenderer = compactSummaryRenderer("work-item-context-summary", "工作项摘要");
const DocumentContextSummaryRenderer = compactSummaryRenderer("document-context-summary", "文档摘要");
// … 一共 14 个，渲染出来是同一张 ProDescriptions 键值表
```

**用户说的"表格"就是 compactSummary 这一族**——ProDescriptions 是键值表，
14 个类型渲染出的是同一张表，只是标题不同。

一行工厂调用，参数只有 `testid` 和一句中文标题。在目录里它们各占一个 `type`、
各有一个 `rendererKey`、各有一个 `XxxRenderer` 常量——**看起来处处不同，跑起来处处一样**。

### 全部凑数族

| 工厂 | 区块数 | 参数差异 | 处置 |
| --- | ---: | --- | --- |
| `stableTabsRenderer` | 17 | 仅 testid + 标题（第三参全同） | 留 1，删 16 |
| `compactSummaryRenderer` | 14 | 仅 testid + 标题 | 留 1，删 13 |
| `facetFilterRenderer` | 6 | 仅 testid + 标题 | 留 1，删 5 |
| `statusStrip` / `commandHeader` / `runtimeControl` | 2+2+2 | 仅 testid + 标题 | 各留 1，删 3 |
| `ScheduleCalendar` | 11 | 换绑定字段名 + create/edit 开关 | 留 1，删 10 |
| `CalendarBlock` | 7 | 同上 | 留 1，删 6 |
| `WizardBlock` / `createWizard` | 3+3 | 仅文案 | 各留 1，删 4 |
| **合计** | | | **删 57，407 → 350** |

### 没砍的（有真实行为差异，留着）

- `matureKanbanRenderer` × 12：`variant` 在函数体里被读 **24 次**，
  backlog / triage / incident 三档会按优先级排序，其余不排。差异浅但真实。
- `diagnosticDrawer` × 2：后三个参数是绑定字段名（`refKey` / `messageKey` / `statusKey`）。
- `multiSeriesChart` × 2：`defs` 是列定义。
- `ImportMappingWizard`：`mapping: true`，跟同工厂另外三个不一样。

## 三、线上影响：零

查了线上 5 个应用（`告警值班台` / `订房通` / `值班哨兵` / `色藏` / `萌宠加分宝`），
一共用到 21 个区块类型。**被删的 57 个一个都没被用到**。

`OnCallScheduleCalendar` 和 `ResourceBookingCalendar` 线上在用，正因为如此
被选为各自那一族的幸存者。

## 四、为什么老的防线没拦住

`slide-rule-python/tests/test_independent_structure_blocks_batch8.py` 里早有一条
名字叫 `..._without_alias_counting` 的棘轮，防的正是"凑数"。但它的判据是

```python
assert len({block["rendererKey"] for block in selected}) == 6
```

**`rendererKey` 唯一**。而这批凑数每个都有自己的 rendererKey——
唯一性检查对"内容相同、标识不同"天然无感。

这是本仓踩过的同一类坑的第三次：判据钉在**标识**上，而问题出在**内容**上。
（前两次：手写的 `uses` 声明 316 个与实际渲染不符；`pageKinds` 声明从没集中评审。）

新闸 `client/src/pages/sliderule/live-runtime/__tests__/no-filler-blocks.test.ts`
换了下手的地方：**同一个工厂被 N 个区块调用时，参数里必须有除 testid/文案之外的差异**。

### 新闸自己也差点写错

第一版按"参数是不是裸字符串"来剥，结果把三族真有差异的判成了凑数——
`matureKanban(variant)`、`diagnosticDrawer(…refKey…)`、`multiSeriesChart(…defs…)`
的差异**恰好都长成字符串**。改成去读工厂签名里的**形参名**才对。

判据里留了一条"签名读不到就一律保留"的退路：**宁可漏判，不可误判**——
误判会逼着人去删真有用的区块。

## 五、顺带掉下来的一格

`test_page_kind_consistency_ratchet` 的矛盾对数 **9 → 8**，
而且**不是靠改 pageKinds 改出来的**：矛盾对里有一对本来就是同一份实现挂着两个名字，
一个允许 workbench 一个不允许。

也就是说这批 pageKinds 矛盾里，至少有一部分根子不在"页型标错"，
而在**"这个类型压根不该存在"**。剩下 8 对值得按这个角度再看一遍。

## 六、还没做

- **幸存者的名字还在撒谎**：`WorkItemDetailTabs` 现在是目录里唯一的 tabs 区块，
  但名字写着"工作项详情页签"——模型只会在工作项类题目上想起它。
  同样问题：`WorkItemContextSummary` / `KubernetesResourceFilter` /
  `DatasourceHealthStrip` / `ExploreQueryControlBar`。应改成通用名。
- 组件库那面墙上 350 个区块里仍有 **127 个没有示例夹具**，卡片上显示
  "这一页还没为它准备示例数据"。没夹具 ≠ 凑数，但用户在墙上看到的稀疏感有它一份。
- `matureKanban` 那 12 个差异很浅，值得再问一遍是不是该收成 3 档（排序/不排序/带 WIP 限制）。

# 第二刀：判据从「源码形状」换成「渲染结果」

第一刀交付后，用户看了组件库那面墙又说：**「我看着主体区、补充说明，怎么还全是表格」**。
他是对的。第一刀的判据（同工厂 + 参数只有 testid/文案）漏了两大类，而且漏得很典型。

## 漏掉的两类

**① 挤在同一行源码里的 16 个**

```ts
const KeyboardCommandPaletteRenderer=ContextPanelRenderer("palette"); const NotificationCenterDrawerRenderer=ContextPanelRenderer("notifications"); const …
```

行锚定的正则只匹到第一个，另外 15 个当场隐身。上一轮统计里 `ContextPanelRenderer`
显示"1 个"，我照单全收了。

**② 根本不是调用点，是策略表条目**

```ts
export const CONFIGURATION_WIZARD_POLICIES = {
  SurveyBuilderWizard: { title:"问卷构建向导", testid:"survey-builder-wizard",
                         operation:"publishSurveyDraft", confirm:"…", requiresChoice:true },
  CheckoutReviewWizard: { …, requiresAcknowledgement:true },
  // … 16 条
}
```

16 个向导，行为标志位（`requiresSelection` / `requiresChoice` / `requiresAcknowledgement`）
只有 **4 种组合**——4 个区块穿了 16 件马甲。用户截图里那一整屏一模一样的
`SurveyBuilderWizard / CheckoutReviewWizard / WorkspaceCreationWizard…` 就是它们。

## 教训

不是"正则写得不够全"。是**判据挂在源码怎么写上，就永远追不完写法**。
所以第二刀换成地基真相：

> 把每个区块用一份**按它自己 bindingSchema 合成的夹具**真渲染一遍，
> 归一化 DOM（扔文本/id/testid/内联样式，class 只留骨架）之后比对。
> 结构全等 = 同一个区块，跟源码写成什么样无关。

## 度量本身也差点出错

第一版量出 114 个"重复"，其中大部分是假的：

| 假重复 | 原因 | 处置 |
| --- | --- | --- |
| 19 个图表判成同款 | ECharts 在 SSR 下只吐一个空容器，漏斗图和热力图 DOM 一样 | 整类排除 |
| 一批未绑定的判成同款 | 都渲染 antd `Empty` | 排除空态 |

**差点因此把 `SankeyFlow` 和 `RadarComparison` 当重复删掉。**
排干净之后是 18 组 52 个，删 34 → 目录 **350 → 316**。

判据定的是**宁可漏判，绝不误判**：误判会逼人删掉真有用的区块，比留几个凑数的贵得多。

## 第二刀删了什么

| 组 | 个数 | 幸存者 |
| --- | ---: | --- |
| 向导（策略表 4 种行为穿 15 件马甲） | 7 + 5 + 3 | ApprovalRoutingWizard（线上在用）/ RecoveryPlanWizard / DataRetentionWizard |
| 筛选条 | 5 | CycleFilterBar |
| 看板 | 4 + 2 + 2 + 2 | DependencyKanban / SwimlaneKanban / IncidentResponseBoard / PortfolioKanban |
| 页签 | 3 | BookingStatusTabs |
| 状态条 | 3 | ClusterHealthStrip |
| 指标卡 | 2 × 4 | 各留 1 |
| 操作条 | 2 × 2 | 各留 1 |
| ContextPanel | 2 × 2 | ExportJobDrawer / AuditDiffDrawer |

⚠ `ContextPanelRenderer` 那 16 个里**只有 4 个是真重复**——量之前我以为整族都是。
它的 `variant` 在函数体里有真分支，多数确实渲染出不同的东西。
**先量再砍，这一条又救了一次。**

## 两刀合计

目录 **407 → 350 → 316**，删 91 个。pageKinds 矛盾对 9 → 8 → **7**，
FieldRef 类型冲突基线 27 → **25**（`typeFieldRef` 和 `facetFieldRef` 随重复类型一起消失）。

两道闸并存，各管一头：
- `no-filler-blocks.test.ts` —— 源码侧：同工厂不许只换文案（快，抓写法）
- `no-duplicate-blocks.test.tsx` —— 渲染侧：两个区块不许渲染出同一个 DOM（慢，抓事实）

# 第三件事：墙上的空卡（这才是"看着一样"的大头）

砍完 91 个之后再看用户那两张截图，会发现剩下的卡片仍然长得差不多——
但那**不是重复**，是每张卡都写着"这一页还没为它准备示例数据"。
手写夹具只覆盖 229/316，其余卡片上只有一行灰色的组件清单。**没东西可看，当然看着都一样。**

补的办法不是再手写 87 份（会一直欠着），是把第二刀那套合成器接进墙：
按目录里本来就有的 `bindingSchema` 现合成绑定，**值仍然取这一页原有的中文示例数据**
（门店巡检那套），所以卡上出现的是"高新店 / 整改说明.docx"这类看得懂的东西，
不是"示例文本 1 / 示例文本 2"。

    真渲染出内容：229/316（72.5%）  →  301/316（95.3%）

判据取的是**结果**不是"有没有夹具"：合成出来的绑定照样可能喂不饱区块
（比如它要日期字段而示例实体没有），那时渲染的还是空态，墙上看着没有任何区别。
`wall-renders-something.test.tsx` 钉的就是这个比例。

剩下 15 个仍是空态，属于合成喂不饱的，需要挑更合适的示例实体——这一档留着。

## 还剩什么

- **幸存者的名字还在撒谎**（第一刀就欠着的）：`WorkItemDetailTabs` 是目录里唯一的
  tabs 区块，名字却写着"工作项详情页签"，模型只会在工作项类题目上想起它。
  同样问题还有 4 个。
- 15 个合成夹具喂不饱的区块仍显示空态。
- 合成绑定偶尔会把数字字段绑到字符串上，渲染时出 `NaN`（控制台有警告，不影响布局）。
