# 绑定契约草案 v1 —— 三种载体，一套词汇

> 状态：**草案**，未实现。依据是 2026-08-13 的七组对照实验
> （`experiments/visual-first/`，分支 `claude/visual-first-model-derivation`）。
> 数字都来自实测，不是估计。

## 一、这份草案要解决什么

今天系统里有三种「页面的表达形态」，各自能力不同，但**它们说的其实是同一件事**：
「这块地方显示什么数据、点了做什么」。三种形态各有一套写法，互不相通：

| 形态 | 载体 | 现有词汇 |
|---|---|---|
| 区块组件 | JSON `blocks[]` | `binding.entityRef` / `binding.fieldRefs` / `onAction` |
| 自由树 | JSON 节点树 | `dataRef` / `rowsRef` / `fieldRef` |
| HTML（新） | HTML 字符串 | —— 没有 |

这份草案的主张：**把它们收成一套词汇**，载体保持各自的（JSON 树 / HTML 属性），
语义完全一致。这样同一个五系统模型能驱动任意一种载体，选哪种是排版决策，
不是能力决策。

## 二、实验结论（决定了这份草案的形状）

七组对照，同模型同契约，只换证据与载体：

| 组 | 形态 | 丰富度（字段数） | 值/行数可驱动 | 结构可迭代 | 功能完整 |
|---|---|---|---|---|---|
| A | 纯意图推模型 | 25 | ✓ | ✓ | ✓ |
| D | HTML 反推模型 → 组件 | **37** | ✓ | ✓ | ✓ |
| F | 模型自己写 JS | 丰富 | ✓ | ✗ | **67%**（六项 12/18） |
| G | 带绑定的 HTML | 丰富 | **✓** | ✗ | 未测 |
| G2 | 字段清单驱动的 HTML | 丰富 | ✓ | **✓** | 未测 |

三条硬结论：

1. **HTML 当输入有效**：A→D，字段 25→37、区块 10→14、臆造 0（A/D 同为 55 字意图，
   唯一差别是有没有 HTML，这一对是干净的）。
2. **让模型现写 JS 不可靠**：F 组六项功能通过 12/18，三份里只有 1 份全过。
   失败形态是**静默**的——能点、不报错、就是没反应，跟线上报的那三个 bug 同型。
3. **HTML 能拿到结构活性，但要一条额外契约**：G 组加字段不跟（模板里没有那个
   `<td>`，Vue 也一样）；G2 加上「字段清单驱动」之后，4 列→5 列，三份全过。

## 三、统一词汇（六个概念）

### 1. `rows` —— 逐行容器（= `v-for`）

这个节点是列表容器，它的**第一个子元素是一行的模板**，按取到的行数重复。

| 载体 | 写法 |
|---|---|
| 自由树 | `{"rowsRef": {"entityRef": "customer", "fieldRefs": [...], "sortByRef": "...", "order": "desc", "limit": 5}}` |
| HTML | `<tbody data-rows="customer" data-sort="next_follow_up_at" data-order="desc" data-limit="5">` |
| 组件 | `binding: {entityRef, fieldRefs, ...}`（由组件自己实现循环） |

### 2. `field` —— 取当前行的某个字段

只在 `rows` 子树内有意义，且必须在该 `rows` 的字段白名单里（自由树已有这条树级校验）。

| 载体 | 写法 |
|---|---|
| 自由树 | `{"fieldRef": "customer_name"}` |
| HTML | `<td data-field="customer_name">` |

### 3. `value` —— 单值（聚合或首行）

| 载体 | 写法 |
|---|---|
| 自由树 | `{"dataRef": {"entityRef": "customer", "aggregate": "count", "trendFieldRef": "created_at", "trendGrain": "day"}}` |
| HTML | `<span data-value="customer" data-aggregate="count" data-trend="created_at" data-grain="day">` |

`aggregate` 合法值沿用现状：`count` / `sum:<字段id>` / `avg:<字段id>`，或省略。

### 4. `fields` —— 字段清单驱动结构 ⭐ 新增

**这是 G2 验出来的那一条，也是这份草案里唯一的新概念。**

`rows` 解决「有几行」，`fields` 解决「有几列」。有了它，往数据模型里加一个字段，
表格自动多一列——`DataTable` 一直是这么工作的，只是从没被写成一条通用契约。

| 载体 | 写法 |
|---|---|
| 组件 | `binding.fieldRefs`（已有，就是这个语义） |
| HTML | `<tbody data-rows="customer" data-fields="*">` + 一个 `<td data-cell>` 单元格模板 |
| 表头 | `<thead data-head="customer">` + 一个 `<th data-col>` 列模板 |
| 自由树 | **缺**（要加 `fieldsRef`） |

`data-fields` 取值：`*`（该实体全部字段）或逗号分隔的字段 id 白名单。

> ⚠️ **边界**：用了 `fields` 的区域，视觉线就不起作用了——列由清单生成、样式由
> 单元格模板决定，图上画的表头和占位行全被丢掉。**这块区域等于重新实现了一遍
> DataTable。** 所以 `fields` 该用在数据密集区，不该用在版式密集区。

### 5. `action` —— 动作 ⭐ 新增

自由树今天**完全没有这一维**（`FreeformNode` 只有 tag/style/text/iconRef/imageRef/
dataRef/chart/rowsRef/fieldRef/children，一个动作字段都没有）。所以自由树画出来的
按钮是「会发光的 div」。

管道其实是通的：`ExperienceBlockRendererProps` 里一直有

```ts
/** Step 5：区块事件触发动作时的回调（actionId, eventData）。 */
onAction?: (actionId: string, eventData?: Record<string, unknown>) => void;
```

`FreeformInsightRenderer` 也是这个类型，只是节点上没东西可以触发它。

| 载体 | 写法 |
|---|---|
| 自由树 | `{"actionRef": {"kind": "navigate", "pageRef": "customer_list"}}` |
| HTML | `<button data-action="edit" data-entity="customer">` |
| 组件 | `onAction("editRequest", {rowId})`（已有） |

**受控动作，只允许两类：**

```
{"kind": "navigate",  "pageRef": "<page_id>"}     跳到某一页
{"kind": "openBlock", "blockRef": "<block_id>"}   打开某个组件区块
```

**不允许直接写数据。** 理由是实测的：F 组让模型自己实现写入，六项通过 12/18；
而写入涉及表单状态、校验、乐观更新、并发冲突——这些组件库已经解决了，
今天修的那三个 bug（查看没反应 / 编辑弹详情 / 表单没校验）全在这条路上，
**修一次所有应用都好**。让 AI 每次现写一遍，错误率不会更低。

所以：**读和跳转归 HTML/自由树，写入永远归组件。**

### 6. `chart` —— 图表（现状保留，不动）

自由树已有 `chart: {type, entityRef, dimensionFieldId, metric, metricFieldId, metricLabel}`。
HTML 侧对应 `<div data-chart="bar" data-entity="customer" data-dimension="source" data-metric="count">`。

## 四、三种载体各用在哪

依据实验：

| 区域性质 | 用什么 | 理由（实测） |
|---|---|---|
| 版式密集：首页、KPI 墙、看板、筛选条 | **HTML / 自由树** | 视觉线给的丰富度全额保留（字段 25→37） |
| 数据密集：表格、详情、列表 | **组件** 或 HTML+`fields` | 要结构活性；用 `fields` 的话 HTML 已退化成壳 |
| 写入、事务、权限 | **只能组件** | F 组 67%，且失败是静默的 |

一句话：**HTML 当输入解决「AI 看不懂这页要什么」，组件当输出解决「功能完整」。**
两者不是二选一，是流水线的两段。

## 五、要动的代码（按收益排序）

1. **自由树加 `actionRef`**（受控跳转两类）
   —— 管道现成（`onAction` 一直在传），改动最小，直接把自由树从「能看」变成「能用」。
2. **`dataRef` 加过滤维度**
   —— 线上实测的真 bug：`aggregate` 只有 count/sum/avg，表达不了「今日」「待审」
   「即将到期」，导致两张语义不同的 KPI 卡都显示同一个数。
3. **自由树加 `fieldsRef`**（对齐 G2 的 `data-fields`）
   —— 让自由树也能做「加字段自动多列」。
4. **HTML 载体的解释器**
   —— G2 那份 55 行的原型已经跑通（`experiments/visual-first/g2_render_test.mjs`），
   语义跟自由树完全一致，可以共用同一套解释逻辑。

## 六、开源参照

- **动作/绑定写在 HTML 属性上**：[Alpine.js](https://github.com/alpinejs/alpine)（15KB、无构建、
  `x-for`/`x-text`/`@click`，语法近 Vue）、htmx、Stimulus。G 组实测 Alpine 那一路能跑通。
- **字段清单驱动结构**：react-jsonschema-form、JSONForms、Formily、amis、jsonTables
  （JSON Schema → ag-Grid 列定义）。
  **全部是 JSON 驱动，没有一个是 HTML 属性驱动的**——G2 跑完就明白为什么：
  一旦结构由清单决定，HTML 模板对那块区域就没有信息量了，多一层反而累赘。
  这也说明我们的自由树（JSON 驱动）本来就在成熟路线上，缺的只是 `actionRef`
  和 `fieldsRef` 两个概念。

## 七、这份草案没有回答的

- **权限和工作流不能从界面反推**。实测：4 份 HTML 里「角色/权限/主管/管理员」
  出现 0 次，「成交/流失/归档/阶段」出现 0 次；五组推出来的流程拓扑完全相同
  （5 节点 6 转移），说明它来自模型的行业常识，不是证据。这两块只能从 spec 来。
- **菜单在多次生成之间不稳**（并发出图导致 4 张图三套菜单，模型收敛后仍有方差）。
  应该由 spec 的 requirement 列表锚定，不该让图去投票。这一项目前没有判据在守。
- **HTML 载体的写入路径**没测（G/G2 只验了读和结构）。按第五节的主张，
  写入本来就不走这条路，但如果将来要走，得先补测。
