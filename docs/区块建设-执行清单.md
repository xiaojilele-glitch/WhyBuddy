### ColumnSettingPanel 实际搬到了什么（第一个走完六步的）

那 605 行 JSX **一行没用**——我们没有 TableContext、没有 Tree、状态形状也不同。
真正拿到的是它替我们踩过的四条边界，每一条自己写都会漏，而且漏了之后界面看
起来是「好的」，只是行为不对：

1. **半选的分母是"面板里真的列出来的列"**，不是状态表全量。它的原话：columnsMap
   里可能有 hideInSetting 的列或运行时被删掉的过期 key，分子分母对不齐。
2. **改了固定必须重排顺序**（issue #9556）。固定分三段、顺序号却是全局的，只改
   固定不重排，「固定在左」的列能排在中段后面。
3. **重置要连顺序一起重置**（issue #9558）。只复位显示状态，下一次挪动仍按旧顺序算。
4. **没有任何固定列时不显示分组标题**，否则一个孤零零的「不固定」挂在那。

两条它没做、我们做了的：

- **全部列被藏起来**时它把一张没有列的表交给 antd Table（渲染出空白表头，像坏了）。
  我们给空态 + 一句「在列设置里勾回来」。
- **面板不另存一份默认列**。第一版我给了面板自己的 `fieldRefs`，浏览器里当场
  露馅：面板说默认 4 列、表格声明 10 列，什么都没动「重置」却可点。列由表格
  声明，面板只负责运行时改它——pro-components 其实也是这么分的，它的重置读的是
  表格的 `columnsState.defaultValue`。

**顺带把 `source: {repo, path, took}` 这个字段开出来了**（schema_legal 校验三项
都得是非空字符串）。`took` 那栏写"学到的是什么"，是三项里最值钱的一个。

### EditableSubTable：这次是"接进契约"，不是重写渲染

`EditableProTable` / `RowEditorTable` / `CellEditorTable` **三个都在我们已装的
pro-components 2.8.10 里导出着**，一个新依赖都不用加。所以活是把它们接到我们的
binding 上（列从 fieldRefs 来、控件类型从数据模型来），再把这几条钉住：

1. **失焦延迟 150ms 才退出编辑**。原注释：焦点在同一行字段间 Tab 切换时，新字段
   的 onFocus 会在 blur 的 setTimeout 回调之前触发，从而取消定时器。立刻退出的话
   用户按一下 Tab 就被踢出编辑。
2. **整行编辑与单元格编辑是两套**。单元格档还要记 activeColumnId 把别的列显式设成
   `editable: false`，不然双击一格整行都变输入框。
3. **列标识是 `${列序号}:${dataIndex}`**，dataIndex 可能缺失也可能重名。
4. **新行分 `dataSource` / `cache` 两种**：前者直接进数据不能取消只能删，后者一取消
   就消失。这是两个不同的业务承诺，不是实现细节。
5. **到行数上限是把新建按钮藏掉**，不是点了再报错。

**顺带改了范式**：`form.main` 的 maxBlocks 从 1 提到 2。证据是 pro-blocks 的
`FormAdvancedForm`——PageContainer 里三张卡，最后一张就是 EditableProTable。
「订单头 + 订单行」是业务表单页最常见的形状，只准放一个的话明细子表无处可去。

### TableToolbar：读完源码判定**不该建成区块**

`ListToolBar` 是「标题 + 搜索 + 操作 + 设置」四段的容器。在我们的模型里这四段
已经各有归属：标题和主操作是 `PageHeader`，设置是刚建的 `ColumnSettingPanel`，
筛选是 `FilterBar`。再建一个 TableToolbar 就是把同一件事讲两遍，模型还得在几个
高度重叠的选项里挑——这正是门禁里 `duplicate-block` 那条规则要挡的事。

它那四段里我们**真正没有的只有关键词搜索**（FilterBar 只做枚举 + 日期范围）。
那是批次 3 的 `SearchBox`，不在批次 1 里，没有顺手做。

读到的两条布局边界记在这里，将来做 header 区排布时用得上：

- **搜索框的位置随有没有标题变**：有标题→搜索去右边；没标题→搜索占左边标题的位置。
- **左边没内容也要留一个空 div 占位**，原注释：「保留dom是为了占位，不然 right
  就变到左边了」。两边都空时整条不渲染，不留一条空白带。

### DragSortTable：做成 DataTable 的一个 prop，不是第四张表

pro-components 那边独立成组件，是因为它得包住 ProTable 的 `components` /
`tableViewRender` 才能塞进 dnd 上下文——**实现约束，不是概念区分**。拖得动的表和
拖不动的表是同一张表。它的 `DragSortTable` 同样在 2.8.10 里导出着，不加新依赖。

拿到的：拖完**先本地生效再回调**（`onDragSortEnd` 收到的是已经排好的新数组，
持久化归调用方——等服务端的话手一松表格会弹回去）；限制纵向轴；拖回原位不触发；
把手挂在指定列而不是整行可拖（整行可拖会和"点一行=选中/查看"抢同一次按下）。

我们额外关掉两样，理由都是手势打架：**分页**（跨页拖没有意义）和**勾选**
（复选框和把手抢同一次按下）。

### MetricGrid：ChartCard 的五槽

它把一张指标卡拆成 `title / action / total / children(迷你图) / footer`。我们此前
只有 `total` 一个槽——一个孤零零的大数字，看不出涨跌也看不出走势。

环比和走势线的算法早就有（`dataref-trend.ts`，当初是给 FreeformInsight 的 dataRef
做的），这次是把它接到指标卡上，**没有重写**。

两条它踩过、照抄的坑：

1. **`0` 是有效值。** 它的 `renderTotal` 第一行是 `if (!total && total !== 0)
   return null`——那个 `&& total !== 0` 就是为这条加的。写成 `!total` 的话，
   「今日新增 0 单」这张卡会整个空掉，看起来像坏了。
2. **内容区高度固定**（`contentHeight=46`）。一排四张卡，有的有迷你图有的只有
   文字，不固定高度就参差不齐——而这排卡正是并列比较用的。

涨跌的颜色照 `Trend/index.less` 逐条核过：`.up` 是 `@red-6`、`.down` 是
`@green-6`，另有 `reverseColor` 整体互换。它把「方向」和「颜色」做成两个开关，
是因为**有些指标下降才是好事**（退款率、故障数）。我们先只做默认那一档，
真遇到反向指标再开，不提前造开关。

**顺带修掉一个对照台上逮到的**：指标卡副标题写的是「合计 · amount」，而旁边
表格的同一列写着「金额」。「同一份数据在两个区块里必须读起来一样」这条纪律的
最后一处漏网。

### ProportionPie：我们此前没有任何「构成」形态

TrendChart 是时间轴，RankedList 是条形名次。「销售额按渠道各占多少」这类问题
用排行是答不好的——排行回答"谁最多"，占比回答"这块饼怎么分"。

1. **环图不是实心饼**（`innerRadius: 0.64`）。中间那块空白不是留白，是用来写
   总计的（它的 `statistic.title.content`）——总量和构成一起看才完整。
2. **关掉图例，改用带引线的标签**（`legend: false` + `label.type: 'spider'`）。
   图例和扇区要靠颜色对应，扇区一多眼睛就对不上了。
3. **渠道切换（全部/线上/门店）是卡片外面的事**，它放在 Card 的 `extra` 里。
   在我们的模型里那是 FilterBar / StatusTabs 的活，通过 targets 连过来，不进
   这个区块的契约。

契约里**没有 limit**：长尾折成「其他」这件事 `foldForPie` 已经在管，折叠阈值
只该有一处。

### RankedList：每行的涨跌是**数据自带的字段**

TopSearch 那张表有一列「周涨幅」带 ↑↓ 箭头。看源码才确认的一件事：那个涨幅来自
`searchData` 里的 `range`/`status`，**不是图表现算的**。现算需要每一行各自的时间
序列，那是另一个量级的事，而且业务系统里这类涨幅本来就存在库里。

所以 `deltaFieldRef` 指的是数据模型里已有的数值字段，我们只负责画箭头。恰好 0
只写数不画箭头（箭头是方向的表示，没方向别画）；字段没填的那行整块不画（没填和
「没有变化」是两回事）。

### SearchBox：批次 1 留下的那个真缺口

批次 1 判定「TableToolbar 不该建成区块」时说过：它那四段里标题/操作是
PageHeader、设置是 ColumnSettingPanel、筛选是 FilterBar，**只有搜索一个都没有**。
这次补上。

搬到的一条判断比控件本身值钱：**搜索词是与筛选并列的独立通道。** ToolBar 里它
住在 `counter.keyWords`，不进筛选表单的 values——所以点「重置」清筛选时，用户刚
敲进去的搜索词不会跟着没了。这两件事在用户心里就是两件事，混成一个状态之后
必然出"我只是想换个筛选，怎么搜索也没了"。

所以 `PageFilterState` 里 `keyword` 是**独立字段**，FilterBar 的 `onReset` 只清
`enumFilters` 和 `dateRange`，一条用例钉住它不碰 keyword。

### TagFilterRow：跟 FilterBar 的区别不是长相，是**多选**

下拉一次只能挑一个值，标签行可以「分类挑三个、负责人挑两个」一起筛。所以它不是
FilterBar 的一个 layout 开关——筛选态的形状都不一样（`string | undefined` vs
`string[]`），混成一个字段之后每个读它的地方都要先判类型。

抄到的：一行一个维度 + 左边固定宽度的标题（StandardFormRow 的两栏）；「全部」
本身是一颗可勾的标签而不是另一个清除按钮。

**两条我们没照抄：**

1. 它的展开是 CSS `max-height: 32px → 200px`，而按钮**只要 `expandable` 为真就
   永远显示**，不判断实际有没有溢出——于是只有三个标签时也挂着一个「展开」，
   点了什么都不变。我们按标签数判，并且把"还有几个"写在按钮上。
2. 它的全选判据是 `getAllTags().length === value?.length`——**只比长度**。筛选态里
   留着一个已被删掉的取值时长度照样相等，「全部」就会错误地亮起来。我们用
   `every(v => picked.includes(v))`。这跟 ColumnSettingPanel 半选分母那条是同一类坑。

### QueryFilterBar：FilterBar 早就是它了，只是收起能力一直没打开

`defaultCollapsed` 此前写死 `false`，于是 QueryFilter 的收起/展开永远不生效。
读源码才知道它自己算得出该不该出这个按钮：

```
needCollapseRender = 总栅格 >= 24 且 控件数 > showLength
showLength = max(1, 24 / span - 1)      ← 减掉的那个 1 是给「查询/重置」留的位置
```

一行几个由屏宽断点决定（576/768/992/1200/1600），窄屏还会从 horizontal 切成
vertical。这些都不用我们算。另外打开了 `showHiddenNum`——收起了几个要写在按钮
上，否则用户不知道后面还有没有东西。

### LightFilterRow：判定不该建

`LightFilter` 是同一件事的另一种长相（药丸式内联、`collapse` 时缩成一个「筛选」
图标）。它跟 FilterBar 的差别**纯粹是外观**，筛选态、目标连线、交互模型全一样。
建成第二个区块只会让模型在两个语义相同的选项里挑。真要这种紧凑长相，是

### 关联单据表：补上一个**一直缺着的概念**

这一批最要紧的不是新控件，是"当前聚焦的是哪一条"。RecordDetail 的注释从建成那天
起就写着「运行时还没有选中态时用第一条」——而"还没有"一直是"没有"。

关联单据表没有它就只能把整张表搬过来。ProfileAdvanced 详情页下面那三张 Table
**各是属于这一单的操作日志，不是全库的日志**。把整张表原样搬到详情页上是最容易
犯的那个错，因为它长得很像"做完了"：界面完全正常，只是给用户看了不属于这条记录
的数据。

做法：`binding.parentRef + viaFieldRef`（DataTable 的一种绑定，**不是新区块**——
关联表和普通表是同一个渲染器，差别全在绑定里）。配套加了 `PageFocusState`，
点表格一行就聚焦那一条。

三条纪律写进了用例：

- 没有聚焦记录时**给空态，不是摊出全部**；
- 聚焦的记录名下没有行时，说的是「没有关联单据」而不是「点新建」——后者是在
  引导用户干一件此处干不了的事；
- **两个键要么都写要么都不写**，只写一个当作没声明。猜错的后果是悄悄多给了数据，
  比不生效严重得多。

**顺带改了范式**：`detail.main` 的 maxBlocks 从 1 提到 3，并接受 `chain`。证据是
ProfileAdvanced 的 PageContainer children 里摆了四张卡——流程进度（Steps）、用户
信息、来电记录、退货详情（三张关联表）。只准放一个的话，「关联单据」和「流程
进度」在详情页上无处可去。这跟批次 2 给 `form.main` 提额度是同一类修正。

### RecordDetail：列数默认跟屏宽走

它写的是 `column={isMobile ? 1 : 2}`。写死列数的详情在窄屏上标签和值会挤成一坨。
而且**同一个组件在两个位置该是两种密度**——它页头那份是 `size=small` + 2 列，正文
那份是 3 列。所以 `columns` 保留显式档位（"1"/"2"/"3"），只把默认值换成响应式。

### HeaderFieldGroup / ProfileBasicLayout：判定不该建

`content` 放 Descriptions、`extraContent` 放 Statistic 这个分工，**我们的区域模型
早就是照它建的**——`headerContent`（accepts entityRows）和 `headerExtra`
（accepts aggregate）两个区域的 evidence 写的就是 ProfileAdvanced。RecordDetail
本来就允许落在 headerContent，MetricGrid 允许落在 headerExtra。再建一个
"页头字段组"就是给同一个位置起第二个名字。

ProfileBasic 同理：它是 `RecordDetail + 一张关联表`，`detail.main` 提到 3 之后
直接就能表达，不需要一个叫"简单详情版式"的区块——**版式是区域的事，不是区块的事**。

### 借它的问题定义，不借它的实现

jeecgboot 的合计行是**把一条合计对象 push 进 dataSource**（`usePopBiz.ts` 的
`handleSumColumn`）。代价是连锁的：每页要少查一条、第一次加载还得把最后一条
弹掉、而那条假行能被排序、能被勾选、能被点开。

antd Table 自带 `summary`：合计行在 tbody 之外、固定在底部、不参与排序与选择。
**同一个需求，正确的位置。**合计算的是全部行不是当前页——用户要的是"这批数据
一共多少"，翻页翻到哪儿不该改变合计。

## ⚠️ 2026-08-08 已执行，结论是**改道**

映射表做了，见 **[区块建设-amis对照.md](区块建设-amis对照.md)**。上面这张表里
「290+ 例子」这个数当不了区块的供给量——量完语料（157 篇文档、190 种词汇）：

- 含页面级组件（crud/table/chart/cards/list）的文档只有 **28** 篇
- 频次前五全在字段层：`form` 918 / `button` 545 / `input-text` 455 /
  `page` 299 / `tpl` 244
- `input-*` 表单控件 **37** 种

**amis 的供给在基础组件与表单控件那一层。**它把"一个字段该用哪个控件"做成
了声明（input-rating / input-range / input-password 各是独立控件），这一点值得
抄；但它变不出 200 个区块。

实际兑现的：区块的表单族此前是全站**第四处**字段判定（读侧 FieldValue、内置
表单 FieldEditor、手机档 PhoneFormField 三处早就共读 `field-value-type.ts`），
而且是更差的一套——枚举一律下拉、boolean/ref/datetime 全掉进文本框、`format`
压根不读。改成共读那张表之后**控件档位 5 种 → 17 种**，零新依赖
（ProFormRate / ProFormSlider / ProFormSwitch / ProFormSegmented 早就装着没用）。

**区块要到 200 个，供给还是走②那条路**（NocoBase / ant-design-pro / refine
的真实页面形状），不是 amis。
