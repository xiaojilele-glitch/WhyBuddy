# 区块建设执行顺序

2026-08-08 定。目标：**区块从 18 个长到能覆盖真实业务，且不靠手搓。**

路线的核心判断（来自 20 个开源项目的调研，见 `区块最佳实践-开源调研.md`）：

> 我们的契约层是插座，开源仓库是零件。别人生产验证过的东西，我们做适配入库，
> 不是发明。真正值钱的不是他们那几行 JSX，是**他们踩过的边界情况**。

我原先在这里列了许可证限制（NocoBase 是 AGPL、h5-Dooring 是 GPL、x-render 没有
license），建议那三个只读设计不抄代码。

**用户明确本项目本身就是开源的，参照不设任何限制。** 这是他的项目、他的决定，
按此执行——16 个仓库全部可参照、可抄。

一个纯事实记录在此，不再重复：WhyBuddy 当前 LICENSE 与 package.json 都写的是
MIT；MIT 吸收 AGPL/GPL 代码之后，合并产物需按 AGPL/GPL 发布。用户接受这个结果。

**仍然记 `source: { repo, path }`**，但理由换成**可追溯**：以后看到某条奇怪的
边界处理，能查到它是从哪个项目学来的、当初为什么那么写。这对我们自己有用。

## 阶段 ① · 契约层封口

**为什么先做**：搬进来的区块得有地方插。契约没定死就开搬，等于边搬边改插座。

三件事，互相独立，可并行：

### ①a 区块分族 `family`

给 18 个区块各贴一个：

```
data     自己取数展示，能独立存在        DataTable / RecordDetail / MetricGrid / TrendChart …
filter   不展示数据，只筛别的区块        FilterBar / StatusTabs
action   不展示数据，对别的区块做事      BatchActionBar / QuickActionPanel
content  纯内容，不绑数据                ContentCard / PageHeader / FreeformInsight
```

思路来源 NocoBase 的 `data-blocks / filter-blocks / other-blocks`（只借结构，
不抄代码）。

**为什么比 `capability` 有用**：capability 说"我干什么"，family 说"我能不能单独
存在"。模型现在只知道 FilterBar 是 `filter`，不知道它离开表格就没有意义。

**验收**：目录里 18 个区块全有 family；给模型的清单里带上它。

### ①b `targets`：区块之间的显式连线

`filter` / `action` 族必须声明自己作用于哪个区块：

```json
"binding": { "targets": ["block-id-of-the-table"] }
```

**这一条修掉一个真 bug**（已复现）：`ComponentsLibraryPage` 的 `visibleRows`
对页面上**所有实体**套同一份 `enumFilters`，只按字段名匹配。一页两张表只要都有
`status` 字段，筛一个就把两个都筛了。

Gate 补三条：
- `target-missing` —— targets 指向的区块不在这一页
- `target-not-data` —— target 不是 data 族（筛一个筛选条没有意义）
- `target-entity-mismatch` —— 两者绑的实体不同（跨表要另外声明关联字段）

再补一条区域顺序规则（这是两根轴唯一真的有关系的地方）：
- `filter-after-target` —— filter 族所在区域必须排在 target 所在区域**之前**，
  否则是"先读内容再筛选"

**同时改**：`filterState` / `selection` 从页面级一坨改成按 target 分开存。

**验收**：造一页两张表（订单 + 客户，都有 status），筛一个另一个不动。

### ①c 字段语义：从推断改成声明，7 种补到 13 种

现在 `fieldSemantic()` 从数据猜（看值像不像日期、有没有枚举选项）。猜就会猜错
——之前 enum 列打印 `frozen` 而不是「已冻结」就是这么来的。

改成：**声明优先，推断兜底**。声明来自数据模型的字段定义。

种类照 `refine` 的 field-inferencers（13 种）+ `x-render` 的 `valueType`：

```
现有 7 种： money number date datetime enum text id
补 6 种：   email url image richtext boolean array/relation
```

**为什么必须在②之前**：搬进来的每个区块只要显示字段就会用到它。先搬 60 个再补
语义，等于回头改 60 个。

**验收**：邮箱出 mailto、链接可点、图片出缩略图，各一条用例。

**已完成（ce5cbe9）。** 三条计划外的东西是做的过程中撞出来的，记在这里：

1. **refine 的日期判据有洞，我们没照抄。** 它展开是「有分隔符 且 dayjs 能
   解析」，实测 `dayjs("u-1")` / `dayjs("SO-2026-001")` / `dayjs("2")` 全部
   `isValid`，而 date 的优先级还高于 relation——外键和单号在它那儿会被判成
   日期。加了一道形状闸（必须以四位年份开头），并用一条用例钉住这个分歧。
2. **DataTable 补了 `fieldRefs`。** 它此前是唯一"会显示字段却不能声明显示
   哪几个"的区块，列全靠派生 + 截断到 8。对照台上十一个字段，截断正好切在
   第八个，新补的三种语义一个都看不见。
3. **RecordDetail 改成与 DataTable 共用 `renderCell`。** 它注释里那句"同一份
   数据在两个区块里必须读起来一样"当初只兑现了枚举一条。

### ①d 只读态（可以往后挪）

照 formily 的 `x-pattern`：`editable / disabled / readOnly / readPretty`。有了它，
**详情区块 = 表单区块的 readPretty 形态**，不用两套渲染器。

**为什么排在 ①c 后面**：它更侵入（要改现有渲染器），而且收益是"搬的时候少搬一
半"。如果 ①a-c 做完想尽快开搬，这一条可以挪到②进行到一半、真的发现在重复搬
"详情版/编辑版"时再做。

## 阶段 ③ · 组件注册表 + 通用渲染器

**触发条件**：②进行到复盘点，且确实看到重复。不要提前做。

现在 139 个基础组件是**只能看的示例**：

```ts
export interface BaseComponentDef {
  name: string;                     // "Table"
  render: () => React.ReactNode;    // ← 零参数演示函数，真组件没暴露
}
```

要做的：

1. **注册表**：`component: Table` 能被名字引用、能接 props
2. **组合 schema**：区块 = `{ component, props, children[], bind{} }` 的树
3. **通用渲染器**：走这棵树——查组件、绑数据、接事件。
   最近的一条路是改造 `FreeformInsight`：它已经能渲染一棵树，只是渲染的是原生
   DOM 标签，不是基础组件
4. **嵌套合法性**：Form.Item 只能在 Form 下这类规则（lowcode-engine 的
   `nestingRule` 思路）

## 阶段 ④ · 灌第二类：amis 的 290+

amis 的例子是**纯 JSON 树**，形状跟我们区块 schema 一样：

```json
{ "type": "crud", "toolbar": [{ "type": "button", "actionType": "dialog",
  "dialog": { "body": { "type": "form", "body": [...] }}}] }
```

供给：**135 个页面例子 + 157 篇组件文档**（每篇里还有多个 schema）。

但它用的是 amis 自己的词汇（`input-text` / `crud` / `dialog`），不是 antd。所以
要一张**类型名映射表**：`amis type → 我们的基础组件 + 默认 props`。

有了③的渲染器 + 这张表，这 290+ 就能批量灌进来。

### ⚠️ 2026-08-08 实测：**这个前提不成立，已改道**

动手前把语料量了一遍（`docs/zh-CN/components/**/*.md` 里所有 `"type"`）：

```
157 篇文档 · 190 种词汇 · 37 种 input-* 控件
但含页面级组件（crud/table/chart/cards/list）的只有 28 篇
频次前五：form 918 · button 545 · input-text 455 · page 299 · tpl 244
```

**重心压在字段和零件那一层，不在区块那一层。**页面级的
`crud`+`table`+`table2`+`cards`+`list` 加起来不到 `form` 一项的三分之一，
而且多是同一个 CRUD 反复演示不同参数，不是 200 个不同形状的区块。

改道结果：这一阶段做成了**把 amis 照出来的断线接上**——区块的表单族此前
是全站第四处字段判定（还是更差的一套：枚举一律下拉、boolean/ref/datetime
全掉进文本框、format 压根不读），改成共读 `field-value-type.ts`，控件档位
5 种 → 17 种。完整的量化、映射表、剩余待办见
**[docs/区块建设-amis对照.md](区块建设-amis对照.md)**。

**区块要到 200 个，供给得另找**——还是②那条路（NocoBase /
ant-design-pro / refine 的真实页面形状，一个一个搬）。

# 阶段②复盘（2026-08-08，搬到第 23 个区块时）

计划里写的触发条件是：**搬到第 20~30 个的时候看一次，哪些逻辑在反复重写？
那就是该抽成 schema 的部分。**

## 找到的不是重复代码，是一条一直在漏的缝

先按计划数了一遍"长得像的东西"，确实有四份页面态：

```
filterState   Record<区块id, {...}>              键是筛选区块自己的 id
columnState   Record<区块id, {...}>              键是目标表格的 id
selection     { rowIds: Record<实体, string[]> }  键是实体
focus         Record<实体, string>                键是实体
```

但真正值得动手的不是它们。查宿主接线时发现：**批次 1-4 给渲染器加的六个 prop，
装配预览全接了，真实运行时（`AppRuntimeScreen`）一个都没接。**

于是这六个 prop 撑起来的区块在真实应用里全是死壳：

| 区块 | 真实运行时的表现 |
|---|---|
| BatchActionBar | 永远显示「勾选左侧的行」 |
| DataTable | 没有勾选列 |
| ColumnSettingPanel | 「没有连到任何表格」 |
| 关联单据表 | 「先选中一条主记录」 |
| TagFilterRow | 勾了标签没反应 |
| SearchBox | 敲了词没反应 |

每一个都**渲染得完全正常**，只是点不动。这正是这个项目已经踩过一次的形状——
QuickActionPanel 拿不到 pageActions，一直渲染成空气，因为它总跟别的区块挤在
一个区里，没人看得出少了谁。

还有第二种漏法，形状不同：`handlePageFilterChange` 是**逐字段重建**的，只重建
`enumFilters` 和 `dateRange`。TagFilterRow 和 SearchBox 发过去的补丁 prop 传到了、
但在 reducer 里被默默吞掉。

## 讽刺的地方

`AppRuntimeScreen` 里那份 `sharedBlockRendererProps` 当初**就是为了防这件事建的**，
它的注释写着「逐个列举等于每加一个 prop 就埋一次漏传」。

但它自己就是逐个列举的，只是把三个调用点收成了一处。加新 prop 时照样要记得回来
补，漏了不报错。**把重复收敛成一处，不等于把漏掉这件事变得会报错。**

## 做了什么

1. **补齐真实运行时的六个通道** + 让 `applyPageFilter` / `handlePageFilterChange`
   认识 `enumMulti` 和 `keyword`。
2. **建护栏** `__tests__/block-props-wiring.test.ts`：渲染器接口里每个 prop，要么
   宿主真的传了，要么写进豁免名单**并说明为什么**。筛选通道单独钉一条：写的人往
   `PageFilterState` 里加一条，读的人（过滤函数 + reducer）就得跟上。
3. **验证护栏真的会红**：人为把改动退回复盘前的状态，用例点名报出
   `selection, onSelectionChange, columnState, onColumnStateChange, focus` 和被吞的
   `enumMulti`。只会绿的护栏等于没有。

顺带补上一条真行为：`rowSelect` 是**区块事件**不是页面动作，而
`handleBlockAction` 第一句就去 `page.pageActions` 里查、查不到直接 return——
所以在真实运行时里**点表格一行一直什么都不发生**。现在它先聚焦再往下走。

## 阶段③要不要提前？—— 不要

四份页面态看着像该统一，但现在统一是错的：

- 按实体存的那两个（选中、聚焦）本来就是实体级概念。一页两张表绑同一个实体时，
  选中态本来就该共享。
- 按区块存的那两个，源/目标的区别是真实的：一个筛选条可以筛两张表（一对多），
  一张表的列设置只属于它自己（一对一）。

硬合成一个 `Record<key, unknown>` 只会把这些区别抹平，然后在每个读的地方重新判
一次。阶段③的触发条件是"真的看到重复"，而这里看到的是**四份各不相同的东西长得
有点像**——那不是重复。

**等到出现第三个"按目标存"的状态、或者真的需要跨实体共享选中态时，再回来看。**

## 这次复盘学到的方法

原来打算找的是"重复的代码"。更该找的是**"加一样东西时要记得改几处"**——因为
重复代码看得见，而漏改看不见，它伪装成一个正常渲染的空状态。

后面每批搬完，除了跑用例，还该问一句：**这次加的东西，在真实运行时那条路上
真的通了吗？**

# 列表页归属：三步走（2026-08-08，用户拍板）

复盘查出"批次 1-4 的积木在最常见的列表页上根本不上屏"之后定的路线。
**骨架从"拥有者"变回"兜底"，它本来就该是这个角色。**

## ① 把三样页面级管道从骨架身上摘下来（不改视觉）

新建表单 / 行详情抽屉 / 演示数据徽标，此前长在固定骨架身上——骨架自己调
setFormOpen / setDetailRow，积木那条路想干同一件事**没有入口**。收成
`pagePipes`，骨架照旧调（行为一模一样），积木也能调。

分层照 nocobase 的 `ActionContext` / `ActionContainer`：**openMode 决定容器
（drawer/modal/page），不由触发它的那个组件决定**。积木只说"打开这条记录"。

积木事件接线：`createRequest` → 新建表单；`editRequest` → 那一行的详情；
`rowSelect` → **只聚焦不弹抽屉**（同页可能已有 RecordDetail）。在这之前这三个
事件全被 `handleBlockAction` 第一句的 pageActions 查找丢掉了。

## ② 翻转默认

判据从「页面形态是什么」换成「**声明了没有**」。形态决定骨架长什么样，决定
不了这一页该由谁画。

兜底：声明了积木但没有 `capability === "entityRows"` 的，仍把内置表格补进
版面——模型漏写一张表就整页没东西看，那是翻转最容易造成的伤害。

**判据用 capability 不用 family**，这条踩过：MetricGrid 的 family 就是 data
（它自己取数、能独立存在），用 family 判会把"只有一张指标卡"的页面判成
"记录已经有人展示了"。**family 回答"能不能独立存在"，capability 才回答
"展示的是什么"。**

顺带：「绑主实体的 DataTable 一律摘掉」改成只在骨架还在时生效。

## ②之后必须改 prompt —— 不改等于没翻

查了 12 个真实应用 / 60 个页面：**100% 声明了 blocks，但 DataTable 出现 0 次**。
原因是 prompt 里白纸黑字写着「每一页都已经自带一张主实体表，**不要**再发
DataTable」。模型完全照做了。

那条措辞写的时候是对的；翻转把前提改掉之后它成了有害指令——教模型别发表格，
而现在不发就真的没有表格。反过来写成「列表页**必须**发一张」。

**真跑验证（1893s 一轮）**：

| | 改之前 | 改之后 |
|---|---|---|
| DataTable 出现 | 0 次 / 60 页 | **5 次 / 6 页** |
| 含表的 workbench 页 | 0 | **4 / 4，全绑主实体** |
| 区块类型种类 | 4 种 | **9 种** |

而且挑得对：monitor 页和 calendar 页没有表（那两档本来就不该有），采购页出了
两张（主实体一张 + 关联实体一张）。三个 filter 族区块全都按 ①b 的契约写了
`targets`，一个没漏。

## ③ 收掉重复的列设置

第②步顺手造出来的重复：积木页的 Card 右上角那个齿轮改的是内置表格的列，而
内置表格已经不渲染了——它不只是重复，是**完全失效**（点开勾一列，屏幕什么都
不变）。

判据是「**内置表格在不在屏幕上**」，不是「有没有 ColumnSettingPanel」。它
governs 谁就跟着谁出现，跟 pro-components 的分法一致（ColumnSetting 是
ProTable `columnsState` 的一个视图）。

**两份列状态故意不合并**：`tableColPrefs` 按页面 id 存（内置表格没有区块 id），
`columnState` 按目标区块 id 存。合并要先给内置表格编个假 id，那是为对称而对称。

    order_list      声明五个积木  → 积木画，骨架让位
    order_nodata    只声明指标卡  → 积木画，内置表格补回来
    order_skeleton  不声明        → 骨架画
