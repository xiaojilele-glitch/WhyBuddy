# 目录窄化评测：翻默认前的大样本验证

2026-08-11。对应清单项 A2（`SLIDERULE_BLOCK_CATALOG_NARROWING` 要不要翻默认）。

复现命令（`scripts/block_selection_metrics.py`，用例定义在
`scripts/data/block_selection_cases.json`）：

```bash
cd slide-rule-python && set -a && . ../.env && set +a
# 关（对照臂）
.venv/bin/python scripts/block_selection_metrics.py --case alert_oncall --narrowing off --runs 6
# 开（处理臂）
.venv/bin/python scripts/block_selection_metrics.py --case alert_oncall --narrowing on  --runs 6
```

> ⚠️ 本报告的数据是在窄化**默认关**的时候跑的，用「设/不设 `SLIDERULE_BLOCK_CATALOG_NARROWING`」
> 区分两臂。2026-08-11 依据本报告把默认翻成了**开**，于是"不设环境变量"不再等于
> 对照臂——上面的命令已改为用 `--narrowing on|off` 显式声明。复跑请照新命令。

## 预先登记的口径（看数据之前定的）

- **主指标**：首轮过闸率，按覆盖域**合并**算——不挑最好看的那个域。
- **次指标**：对题件被选中数。
- **样本**：3 个覆盖域 × 2 臂 × n=6，全部用**当前代码**新跑。历史模型的 prompt
  版本各不相同，混用会把「prompt 版本」和「窄化」混淆。
- `pharmacy_inventory` **不参与**主指标：自适应判定下它两臂的系统提示逐字相同
  （置信度 0.110 < 阈值 0.200 → 退回全量），跑它只是烧钱。

## 结果

两个完整域，各臂 n=6（共 24 趟）：

| 用例 | 臂 | 首轮过闸 | 对题件被选中（逐趟） |
|---|---|---|---|
| alert_oncall | 关 | 5/6 | `0, 0, 2, 0, 1, 0` |
| alert_oncall | **开** | **6/6** | **`6, 5, 3, 7, 3, 1`** |
| booking_scheduling | 关 | 5/6 | `0, 1, 0, 1, 1, 2` |
| booking_scheduling | **开** | **6/6** | **`2, 2, 2, 2, 2, 4`** |

合并：

| 指标 | 关 | 开 | 检验 |
|---|---|---|---|
| 首轮过闸 | 10/12（83%） | 12/12（100%） | Fisher 双尾 p≈0.48 —— **无差异** |
| 对题件被选中（均） | 0.67，区间 [0,2] | **3.25**，区间 [1,7] | Mann-Whitney 单尾精确 **p=0.00004** |
| prompt 字符 | 160,528 | 53,298 | −67% |

## 怎么读这组数

**1. 窄化的价值在选材相关性，不在过闸率。**
对题件被选中从 0.67 涨到 3.25，接近 5 倍，精确检验 p=0.00004。而过闸率
83% → 100% **在统计上读不出差异**（n=12，p≈0.48）。

这跟本场早期的印象不同，原因很清楚：过闸率的提升**来自那几条确定性修复**
（pageBindings.workflowRef、区块槽位越界、layout 面板 ref 撞车），它们对两臂
一视同仁地生效，把对照臂也抬到了 83%。窄化在这个指标上已经没有多少空间可让。

**2. 两组分布并非完全不重叠**（关的最高 2，开的最低 1），所以不是"必然更好"，
是"分布明显右移"。

**3. 只有两个域拿到了完整对照**（见下），所以这个结论的外部效度仍以两个域为限。

## release_deployment 的对照臂被上游挡住了

那一格 **12/12 全部 HTTP 400**（`Upstream request failed`，`api.rcouyi.com`
网关），两个波次、并发 12 与并发 3 都复现。同时：

- `release_deployment` + **开** → 6/6 成功
- `alert_oncall` + **关** → 成功（事后再探仍成功）

而窄化关时三个用例的系统提示是**逐字相同的**（都是模块级那份全量常量），差别只有
那一百来字的题面。所以这不是本仓库的代码问题，是上游网关对该请求的系统性拒绝，
我没有进一步定位第三方网关的手段。

该域因此只贡献处理臂数据：过闸 6/6、对题件被选中均 3.67。

⚠️ 顺带一个**提示性**（不是证明性）观察：失败的恰恰是 16 万字符的全量请求，而
5.3 万字符的窄化请求同题 6/6 成功。即便根因是网关不稳，**更小的请求对这类故障
的暴露面更小**。这一条不足以单独支持任何决定。

## 建议

**倾向翻默认**，依据：

1. 选材相关性大幅且显著改善（p=0.00004），这正是最初要解决的问题；
2. 过闸率无回归（83% → 100%）；
3. 目录零覆盖的域已有自适应兜底——`pharmacy_inventory` 置信度 0.110 低于阈值，
   系统提示与全量**逐字相同**（有测试钉住），不再重现 B1 阴性对照测出的 −58%；
4. prompt 省 67%。

**翻之前仍建议补的两件事**：

- `release_deployment` 的对照臂——等上游恢复后补齐，让三个域都有完整对照；
- 域覆盖面。目前 4 个用例里 3 个覆盖域都集中在目录建得厚的地方
  （Alert / Booking / Release）。真实用户题目的域分布未知，而 B1 已经证明
  零覆盖域上窄化本身是净负面（靠自适应兜住，不是靠窄化本身变好）。

## 补记：自适应 limit（2026-08-11，清单 A3 已做）

「窄到多少」改成由分数曲线决定：保留得分 ≥ 0.20 × 最高分 的候选，钳在
[30, limit] 之间（只收窄、不放宽）。按 α 扫召回选出来的：

|  | 固定 N=60 | α=0.25 | **α=0.20（采用）** |
|---|---|---|---|
| alert | 14/16 | N=31 召回 13/16 | N=37 召回 **14/16** |
| booking | 15/15 | N=45 召回 15/15 | N=58 召回 **15/15** |
| release | 17/17 | N=40 召回 17/17 | N=50 召回 **17/17** |

0.20 是**保住与固定 60 完全相同召回**的最激进取值；再紧一档 alert 就掉一个对题件。

⚠️ 这里量到的是「同样召回、候选少 ~20%」。「候选更少 → 选材更准」是
arXiv 2605.24660 的结论（BFCL 上 2 条候选选对 93.1%、5 条降到 87.1%），**本仓库
没有实跑验证过这一步的端到端收益**——没有为它单独跑 LLM 对照。所以别把它宣传成
"选材又变好了"，目前只能说"更省而没有变差"。

用 `SLIDERULE_BLOCK_CATALOG_NARROWING_CUTOFF` 可覆盖那个 0.20。
